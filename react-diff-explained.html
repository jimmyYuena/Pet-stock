一、为什么需要 Diff 算法

React 的核心思想是 UI = f(state)：状态变化时重新生成一棵虚拟 DOM 树（React Element 树）。如果每次都把整个真实 DOM 推倒重建，代价极其昂贵。因此 React 需要比较新旧两棵树，找出最小的变更集合，只把这些差异应用到真实 DOM 上——这个比较过程就是 Diff（协调 / Reconciliation）。

问题：传统的树编辑距离算法（Tree Edit Distance）复杂度是 O(n³)。1000 个节点就要进行约 10 亿次比较，完全不可用。

React 的答案：基于两个符合实际的假设做启发式优化，将复杂度降到 O(n)：

① 两个不同类型的元素会产生不同的树；
② 开发者可以通过 key 提示哪些子元素在多次渲染中保持稳定。

二、三大 Diff 策略

策略内容效果
Tree Diff只比较同一层级的节点，不跨层级比较避免了 O(n³) 的全树对比
Component Diff类型不同的组件直接替换整棵子树省去对不同类型组件的深入比较
Element Diff同层级的一组子节点用 key 区分，支持复用与移动把"删除+新建"优化为"移动"

三、Tree Diff：只做同层比较

React 对两棵树进行分层遍历，只比较同一层级、同一位置的节点。如果一个节点在新树中跨层级移动了（比如从父节点 A 下移到父节点 B 下），React 不会识别为"移动"，而是：在旧位置删除整棵子树，在新位置重新创建整棵子树。

旧树
    A
   / \
  B   C
  |
  D
新树（D 移到 C 下）
    A
   / \
  B   C
      |
      D
React 实际执行
删除 B 下的 D
在 C 下新建 D
（而非移动）

启示：不要做跨层级的 DOM 移动操作。保持 DOM 结构稳定，用 CSS 显隐（或条件渲染同层节点）代替节点搬家。

四、Component Diff：类型不同，整树替换

比较两个节点时，React 首先看 type：

类型相同（如都是 <div>，或都是同一个组件 <Counter />）：保留底层 DOM 节点 / 组件实例，只更新变化的属性（props、style、className 等），然后递归比较子节点。组件的 state 得以保留。

类型不同（如 <div> 变成 <p>，或 <Counter /> 变成 <Timer />）：直接卸载旧树（触发 unmount、state 销毁），完整地重建新树。即使两棵子树内容几乎一样，React 也不会去比较。

// 类型从 div 变为 p：Counter 会被卸载重建，state 丢失
<div><Counter /></div>   // 旧
<p><Counter /></p>       // 新

// 类型相同：只更新 className，Counter 的 state 保留
<div className="before"><Counter /></div>
<div className="after"><Counter /></div>

五、Element Diff：同层子节点与 key

当一个节点有多个子节点时（典型场景：列表渲染），React 需要判断哪些子节点可以复用。没有 key 时，React 只能按索引位置逐一对比：

// 在头部插入一项，没有 key：
旧: [A, B, C]
新: [X, A, B, C]

// 按位置对比：0号 A→X（更新），1号 B→A（更新），
// 2号 C→B（更新），3号新建 C —— 全部节点都被改动！

有了 key，React 就能用 key 匹配新旧节点，识别出"这些节点只是换了位置"，从而复用 DOM，只做必要的移动：

旧: [A(key=a), B(key=b), C(key=c)]
新: [X(key=x), A(key=a), B(key=b), C(key=c)]

// 通过 key 匹配：A、B、C 原样复用，只新建 X 插入头部 ✓

移动判定：lastPlacedIndex（旧版称 lastIndex）

匹配到可复用节点后，React 用一个游标记录"已处理的可复用节点在旧列表中的最大位置"。遍历新列表时：

若当前节点在旧列表中的位置 oldIndex ≥ lastPlacedIndex，说明相对顺序没变，原地保留，并更新 lastPlacedIndex = oldIndex；若 oldIndex < lastPlacedIndex，说明它被排到了更靠后的位置，需要移动。

推论：把最后一个节点移到最前面（如 ABCD → DABC），会导致 A、B、C 全部被标记移动（D 的 oldIndex=3 把 lastPlacedIndex 抬高了）。尽量避免"把尾部节点前移"的操作。

七、Fiber 时代的 Diff（React 16+）

React 16 用 Fiber 架构重写了协调器，但 Diff 的三大策略不变。区别在于实现方式：

每个节点对应一个 Fiber 节点，通过 child（第一个子节点）、sibling（下一个兄弟）、return（父节点）三个指针连成链表，使渲染工作可以被打断和恢复（可中断的并发渲染）。同时维护 current（当前屏幕上的树）与 workInProgress（构建中的树）双缓存，diff 就发生在"新的 JSX 结果 vs current Fiber 树"之间。

子节点列表的两轮遍历（reconcileChildrenArray）

第一轮：新旧列表从头同时遍历，逐个比较 key。key 相同则复用（type 相同）或新建（type 不同），key 不同立即跳出第一轮。这一轮高效处理最常见的"列表基本没变，只更新了内容"的场景。

第二轮：把剩余的旧节点放进一个 Map（key → fiber），再遍历剩余的新节点去 Map 中找可复用的节点，配合 lastPlacedIndex 判断是否移动。遍历结束后，Map 中剩下的旧节点统一删除。

// 简化的第二轮逻辑
const existingChildren = mapRemainingChildren(oldFiber);  // key → fiber
for (; newIdx < newChildren.length; newIdx++) {
  const matched = existingChildren.get(key ?? newIdx);
  if (matched) {
    if (matched.index < lastPlacedIndex) markMove();   // 移动
    else lastPlacedIndex = matched.index;              // 原地
  } else {
    createFiber();                                      // 新建
  }
}
existingChildren.forEach(deleteChild);                   // 删除剩余

八、两轮遍历详解：跳出之后发生什么

1. 第一轮为什么"key 不同立即跳出"

第一轮的假设是：列表的头部顺序没变（最常见的场景是只改了内容、或只在尾部增删）。所以它用两个游标同步走新旧列表，每个位置调 updateSlot 比较 key：

key 相同且 type 相同 → 复用旧 fiber；key 相同但 type 不同 → 删旧建新，还能继续往下走；key 不同 → updateSlot 返回 null，说明"按位置一一对应"的假设被打破了（发生了插入 / 删除 / 换序），继续按位置比下去只会全错，于是立刻 break，把剩下的活交给后续处理。

2. 跳出之后的三种情况

break 之后先看是不是两种"免费"情况，能提前结束就不进第二轮：

情况 A · 新列表走完了（newIdx === newChildren.length）→ 旧列表剩下的全是多余的，统一删除，结束。对应"尾部删除"。

情况 B · 旧列表走完了（oldFiber === null）→ 新列表剩下的全是新增的，逐个创建追加，结束。对应"尾部新增"。

情况 C · 两边都有剩余 → 才进第二轮：剩余旧 fiber 建成 Map(key → fiber)，把"按位置找"升级为"按 key 找"，配合 lastPlacedIndex 判断移动，最后 Map 里没被认领的旧节点全删。

3. 和 beginWork 的关系：不是并列，是包含

这是层级关系，不是两种算法。beginWork 是 Fiber 工作循环里"处理单个节点"的阶段：它先尝试 bailout（props / state 没变就跳过整棵子树），然后执行组件得到新的子元素 JSX，最后调用 reconcileChildren 做 diff——子元素是数组时，走的就是上面的 reconcileChildrenArray 两轮遍历。

workLoop（可中断的循环）
 └─ performUnitOfWork(fiber)
     └─ beginWork(current, workInProgress)   ← 处理"一个节点"
         ├─ 尝试 bailout（没变化就跳过整棵子树）
         ├─ 执行组件，得到新的子元素 JSX
         └─ reconcileChildren(...)            ← diff 发生在这里
             └─ 子元素是数组 → reconcileChildrenArray（两轮遍历）

两个关键推论：① diff 不是"先把两棵树整体比完再更新"，而是逐节点、逐层进行——每个 fiber 的 beginWork 只 diff 自己直接子节点那一层，然后深度优先走到子节点继续；② 正因为 diff 被拆进了每个 fiber 的 beginWork 里，工作循环才能在任意 fiber 之间暂停 / 恢复（并发渲染），而不是一个不可打断的大递归。

九、最佳实践总结

✅ 列表渲染始终提供稳定且唯一的 key（如数据库 id），不要用随机数。

✅ 保持组件类型和 DOM 结构稳定，条件渲染尽量不改变节点类型。

✅ 避免跨层级移动节点；避免把尾部节点移到头部的大规模重排。

❌ 不要用数组索引当 key（列表会增删/排序时）：插入或删除会导致 key 与数据错位，引发大量无效更新，甚至输入框内容、组件 state 串位的 bug。列表纯静态且永不重排时，索引 key 才可接受。
